# Binance Trade Executor (바이낸스 거래 실행가) — Foundational Knowledge

## 역할 정의

바이낸스 거래 실행가는 **투자 결정이 내려진 후 실제 주문을 최적의 조건으로 체결**하는 전문 에이전트다. 분석이나 전략 수립은 담당하지 않는다. "BTC를 $96,000에 0.05 BTC 매수하라"는 명령을 받으면, 그 주문을 최소 비용·최소 슬리피지·최소 시장 충격으로 실행하는 것이 이 에이전트의 존재 이유다.

핵심 가치: **실행 품질(execution quality)**. 같은 주문이라도 실행 방법에 따라 0.1~2%의 비용 차이가 발생하며, 이는 연간 복리로 상당한 수익률 차이를 만든다.

## 핵심 개념

### 1. 주문 유형 선택 기준 (Order Type Selection)

**Market Order (시장가)**
- 즉시 체결이 보장되지만 슬리피지 발생 가능
- **사용 조건**: 체결 속도가 가격보다 중요할 때 (급등/급락 시 손절, 빠른 진입 필수)
- **위험**: 유동성 얇은 시간대에 대량 시장가 주문 시 호가창 여러 단계를 소비하며 예상보다 높은 가격에 체결
- **비용**: Taker fee 적용 (기본 0.1%, BNB 결제 시 0.075%)

**Limit Order (지정가)**
- 원하는 가격 이하에서만 체결. 슬리피지 제로
- **사용 조건**: 대부분의 정상 거래. 시간 여유가 있을 때
- **위험**: 미체결 리스크. 가격이 닿지 않으면 영원히 체결 안 됨
- **비용**: Maker fee 적용 가능 (기본 0.1%, BNB 결제 시 0.075%; 상위 VIP에서 0.02% 이하)

**Stop-Limit Order**
- Stop price 도달 시 Limit order가 자동 제출
- **사용 조건**: 손절(Stop Loss) 또는 돌파 매수(Breakout Entry)
- **주의**: Stop price와 Limit price 사이 갭을 두어야 급락 시 미체결 방지. 보통 0.5~1% 갭 권장

**OCO (One-Cancels-the-Other)**
- Take-profit + Stop-loss를 한 쌍으로 설정
- **사용 조건**: 진입 후 이익 실현과 손절을 동시에 걸어둘 때
- **주의**: OCO는 주문 2개로 카운트됨 (EXCHANGE_MAX_ORDERS 필터, MAX_NUM_ORDERS 필터 모두 적용)

**Trailing Stop Order**
- trailingDelta 파라미터로 가격 추적 비율 설정
- **사용 조건**: 추세 추종 시 이익 극대화. 상승 중 일정 % 하락 시 자동 매도
- **주의**: 변동성 높은 시장에서 delta 너무 작으면 노이즈에 조기 체결

**Iceberg Order (빙산 주문)**
- icebergQty 파라미터로 보이는 수량 제한, 나머지는 숨김
- **사용 조건**: 대량 주문 시 시장 충격 최소화
- **제약**: timeInForce 반드시 GTC 설정 필요. LIMIT, STOP_LOSS_LIMIT, TAKE_PROFIT_LIMIT과 조합 가능
- **전략**: 전체 수량의 10~20%만 노출. 예: 1 BTC 매수 시 icebergQty=0.1

### 2. 슬리피지(Slippage) 최소화

슬리피지 = 예상 체결가와 실제 체결가의 차이.

**발생 원인**:
- 주문 크기 > 최우선 호가 잔량 (호가 여러 단계 소비)
- 유동성 부족 시간대 (아시아 새벽 2~6시 UTC+9)
- 급격한 가격 변동 (뉴스, 청산 캐스케이드)

**측정 방법**:
```
슬리피지(%) = |실제 평균 체결가 - 주문 시점 mid price| / mid price × 100
```

**대응 전략**:
1. **호가창 깊이 사전 확인**: 주문 전 GET /api/v3/depth 호출. 주문 크기가 상위 5개 호가 합산 잔량의 10% 이하면 안전
2. **Limit Order 우선 사용**: 시장가 대신 최우선 매도호가 근처 지정가
3. **주문 분할**: 대량 주문은 여러 건으로 분할 (아래 Order Splitting 참조)
4. **유동성 높은 시간대 활용**: 유럽+미국 겹치는 시간 (UTC 13:00~17:00, 한국 22:00~02:00)

### 3. 시간대별 유동성 패턴

바이낸스는 24/7 운영이지만 유동성은 시간대별로 크게 다르다:

| 시간대 (UTC) | 시간대 (KST) | 유동성 | 특성 |
|---|---|---|---|
| 00:00-04:00 | 09:00-13:00 | 중간 | 아시아 오전, 한국/일본 거래 활발 |
| 04:00-08:00 | 13:00-17:00 | 중-낮 | 아시아 오후, 유럽 아직 미참여 |
| 08:00-12:00 | 17:00-21:00 | 높음 | 유럽 개장, 아시아 일부 겹침 |
| 12:00-16:00 | 21:00-01:00 | **최고** | 유럽+미국 겹침. 스프레드 최소 |
| 16:00-20:00 | 01:00-05:00 | 높음 | 미국 메인 세션 |
| 20:00-24:00 | 05:00-09:00 | **최저** | 미국 야간, 아시아 아직 미시작 |

**실행 규칙**:
- 대량 주문($10K+): 유동성 최고 시간대(KST 21:00-01:00)에 실행
- 소량 주문($1K 이하): 시간 무관
- 긴급 손절: 시간 무관, 즉시 실행

### 4. 수수료 최적화 (Fee Optimization)

**Spot 수수료 구조 (2025-2026)**:

| VIP 등급 | 30일 거래량 | Maker | Taker | BNB 할인 적용 |
|---|---|---|---|---|
| Regular | < $1M | 0.1000% | 0.1000% | 0.0750% / 0.0750% |
| VIP 1 | >= $1M | 0.0900% | 0.1000% | 0.0675% / 0.0750% |
| VIP 2 | >= $5M | 0.0800% | 0.1000% | 0.0600% / 0.0750% |
| VIP 3 | >= $10M | 0.0420% | 0.0600% | 0.0315% / 0.0450% |

**Futures 수수료**:

| 등급 | Maker | Taker |
|---|---|---|
| Regular | 0.0200% | 0.0500% |
| VIP 1 | 0.0160% | 0.0400% |
| VIP 9 | 0.0000% | 0.0170% |

**비용 절감 전략**:
1. **BNB로 수수료 결제**: 25% 할인 (Spot), 10% 할인 (Futures). 항상 소량 BNB 보유 필수
2. **Maker 주문 우선**: Limit order를 현재가에서 약간 유리하게 설정하여 maker로 체결
3. **USDC 페어 활용**: 일부 USDC 페어는 taker fee가 0.095%로 약간 낮음
4. **수수료 vs 슬리피지 트레이드오프**: maker 체결 대기 중 가격이 불리하게 움직이면 taker로 즉시 체결하는 것이 오히려 저렴할 수 있음. 0.025% 수수료 차이 vs 0.1% 가격 이동 → taker가 유리

### 5. 주문 분할 전략 (Order Splitting)

**분할이 필요한 조건**:
- 주문 크기 > 최우선 호가 잔량의 20%
- BTC 기준: 1 BTC 이상, ETH: 10 ETH 이상, 알트코인: 호가창 확인 필수

**Iceberg 방식**:
- Binance 내장 기능. icebergQty 파라미터 사용
- 장점: 단일 API 호출, 자동 분할
- 단점: 알고리즘 트레이더들이 iceberg 패턴 감지 가능

**수동 TWAP (Time-Weighted Average Price)**:
Binance는 2025년 12월부터 조건부 주문을 algo order endpoint로 자동 라우팅. 수동 TWAP 구현:
```
총 수량을 N 등분 → T 간격으로 Limit order 제출 → 미체결 시 가격 조정 후 재제출
```
- **권장 설정**: N=5~10, T=30초~5분
- **주의**: 각 주문마다 API weight 소모. Rate limit 고려 필수

**분할 기준표**:

| 주문 크기 (USD) | 분할 수 | 간격 | 방식 |
|---|---|---|---|
| < $1,000 | 1 (분할 불필요) | - | Limit or Market |
| $1,000 - $5,000 | 2-3 | 1분 | Iceberg |
| $5,000 - $20,000 | 5-8 | 2-5분 | 수동 TWAP |
| $20,000+ | 10+ | 5-10분 | 수동 TWAP + 호가 모니터링 |

### 6. Futures vs Spot 실행 차이

| 항목 | Spot | Futures (USDT-M) |
|---|---|---|
| 수수료 | 0.1% base | 0.02%/0.05% base |
| 레버리지 | 없음 | 1x~125x |
| 청산 리스크 | 없음 | 있음 (Maintenance Margin) |
| Funding Rate | 없음 | 8시간마다 (양/음 변동) |
| 주문 유형 | 기본 + OCO | 기본 + Conditional (자동 algo 라우팅) |
| 포지션 모드 | 없음 | One-way / Hedge |

**Futures 실행 시 추가 고려사항**:
- Funding rate이 높을 때(>0.03%) 롱 진입은 불리 → 비용 선반영
- Reduce-only 주문으로 안전한 포지션 축소
- Mark Price vs Last Price 차이 확인 (청산은 Mark Price 기준)

## 베스트 프랙티스

### Pre-Execution Checklist

1. **호가창 깊이 확인**: `GET /api/v3/depth?symbol=BTCUSDT&limit=20`
   - 주문 크기 대비 호가 잔량 비율 확인
   - Bid-Ask 스프레드 확인 (정상: BTC 0.01%, 알트코인 0.05~0.3%)

2. **BNB 잔고 확인**: 수수료 결제용 BNB가 충분한지 (예상 수수료의 1.5배)

3. **현재 시간대 유동성 판단**: KST 05:00-09:00이면 대량 주문 지연 고려

4. **최근 변동성 확인**: 24h 변동률 >5%면 슬리피지 증가 예상, 주문 분할 강화

### Execution Flow

```
명령 수신 → 호가창 분석 → 주문 유형 결정 → 분할 여부 판단
  → 주문 제출 → 체결 모니터링 → 부분 체결 처리 → 결과 보고
```

### Partial Fill (부분 체결) 처리

1. Limit order 제출 후 `executedQty` 모니터링
2. **30초 내 50% 미만 체결**: 가격을 mid price 방향으로 조정
3. **60초 내 미체결**: 잔여분 취소 후 현재 호가 기준 재주문
4. **긴급 주문**: 잔여분을 market order로 즉시 체결

### API 사용 패턴

```
# Weight 효율적인 호출 순서
1. GET /api/v3/depth (weight: 5-50)     → 호가 확인
2. POST /api/v3/order (weight: 1)       → 주문 제출
3. GET /api/v3/order (weight: 4)        → 체결 확인
4. DELETE /api/v3/order (weight: 1)     → 미체결 취소
```

## 주의사항 / 안티패턴

### 절대 하지 말 것

1. **유동성 확인 없이 대량 시장가 주문 제출**: 알트코인에서 $5,000 시장가 주문으로 5~10% 슬리피지 발생 가능
2. **Stop-Loss 없이 레버리지 포지션 유지**: 청산 리스크. 반드시 OCO 또는 Stop-Limit 동시 설정
3. **Rate Limit 무시**: IP당 1200 weight/분, 주문 10건/초, 100,000건/일 초과 시 밴
4. **단일 API 호출에 의존**: 네트워크 오류로 주문 상태 불확실 시, 중복 주문 방지를 위해 newClientOrderId 활용
5. **Market order로 양쪽 동시 체결 시도**: Spot에서 buy + sell 동시에 market order면 스프레드만큼 즉시 손실

### 흔한 실수

- **Minimum notional 미확인**: 각 페어마다 최소 주문 금액 존재 (BTC: ~$5, 알트: $10~). `GET /api/v3/exchangeInfo` 확인
- **Lot size 미준수**: stepSize 단위로만 수량 지정 가능. 0.001 BTC 단위면 0.0015는 거부
- **Timestamp 동기화 실패**: 서버와 1000ms 이상 차이 나면 요청 거부. `GET /api/v3/time`으로 동기화
- **Stop price와 Limit price 동일 설정**: 급락 시 limit에 안 걸려 미체결. 최소 0.3~0.5% 갭

## 판단 기준

### 주문 유형 결정 플로우

```
긴급도 HIGH (손절/긴급진입)?
  → YES: Market Order (슬리피지 감수)
  → NO: 주문크기 > 호가잔량 20%?
    → YES: Iceberg 또는 TWAP 분할
    → NO: Limit Order (best ask/bid 근처)
```

### 슬리피지 허용 기준

| 자산 | 정상 슬리피지 | 경고 수준 | 거부 수준 |
|---|---|---|---|
| BTC/USDT | < 0.02% | 0.05% | 0.1% |
| ETH/USDT | < 0.03% | 0.08% | 0.15% |
| 대형 알트 (SOL, XRP) | < 0.05% | 0.15% | 0.3% |
| 중소형 알트 | < 0.1% | 0.3% | 0.5% |

### 주문 분할 기준

- 주문 금액이 해당 페어 24h 거래량의 0.01% 초과 시 분할 권장
- 호가창 상위 5단계 합산 잔량의 30% 초과 시 반드시 분할

### 수수료 최적화 의사결정

```
예상 체결 시간 < 5초?
  → Taker 불가피. BNB 결제로 0.075%
예상 체결 시간 < 60초?
  → Maker 시도 (best bid/ask에 limit). 미체결 시 taker 전환
시간 여유 충분?
  → Post-only limit order (maker 보장). 즉시 taker 체결되면 주문 거부
```

### Error Handling 기준

| 에러 코드 | 의미 | 대응 |
|---|---|---|
| -1021 | Timestamp 오차 | 시간 동기화 후 재시도 |
| -1015 | Too many orders | 30초 대기 후 재시도 |
| -2010 | Insufficient balance | 잔고 재확인, 주문 크기 조정 |
| -1013 | Invalid quantity | stepSize/minQty 확인 후 수량 보정 |
| -1111 | Precision over max | 소수점 자릿수 확인 후 절삭 |
| 5xx | Server error | 3초 후 재시도, 3회 실패 시 중단 보고 |

### Market Impact 추정 공식

```
예상 슬리피지(%) = 주문크기(USD) / (상위 10호가 합산 잔량(USD) × 2) × 100

예시: $10,000 주문, 상위 10호가 합산 = $50,000
  → 예상 슬리피지 = 10000 / (50000 × 2) × 100 = 10%  ← 분할 필수!

예시: $1,000 주문, 상위 10호가 합산 = $500,000
  → 예상 슬리피지 = 1000 / (500000 × 2) × 100 = 0.1%  ← 안전
```
