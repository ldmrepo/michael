## 레이어별 상세

### Layer 0: 사용자 (동명)

| 항목 | 내용 |
|------|------|
| **역할** | 시스템의 오너. 목표 설정, 최종 승인권 |
| **행동** | 목표(Mandate) 설정, 제안 승인/거절, 수동 명령 |
| **인터페이스** | Telegram 앱 (모바일/데스크톱) |

사용자가 하는 일:
- "월 수익 3~5%, MDD -15%" 같은 목표 설정
- 마이클의 매수/매도 제안에 [승인] 또는 [거절]
- "포트폴리오 현황", "BTC 분석해줘" 같은 수동 요청
- 목표 변경 (드물게)

사용자가 하지 않는 일:
- 직접 거래소 로그인해서 매매
- 시장 모니터링
- 데이터 수집/분석

---

### Layer 1: 채널 (Telegram)

| 항목 | 내용 |
|------|------|
| **구현** | `src/channels/telegram.ts` (Telegraf) |
| **역할** | 사용자 ↔ 시스템 사이의 유일한 창구 |
| **프로토콜** | Telegram Bot API |

**위로 (사용자 방향):**
- 모닝 브리핑, 이브닝 리캡 전송
- 거래 제안 + 인라인 버튼 ([승인] [거절])
- 긴급 알림 (PRICE_CRASH 등)
- 주간/월간 리포트

**아래로 (시스템 방향):**
- 사용자 메시지 → Gateway로 전달
- 버튼 콜백 (승인/거절) → Gateway로 전달

**원칙**: Telegram은 **배달부**. 메시지를 전달할 뿐, 내용을 해석하지 않는다.

---

### Layer 2: 게이트웨이 (Gateway)

| 항목 | 내용 |
|------|------|
| **구현** | `src/core/gateway.ts` (WebSocket :18789) |
| **역할** | 모든 컴포넌트 사이의 중앙 메시지 라우터 |
| **프로토콜** | WebSocket JSON 메시지 |

```
메시지 포맷:
{
  from: "telegram" | "sentinel" | "michael" | "scheduler",
  to:   "michael" | "telegram" | "agent:{name}",
  type: "message" | "trigger" | "report" | "command",
  payload: { ... }
}
```

**라우팅 규칙:**
- `from: telegram` → `to: michael` (사용자 요청)
- `from: michael` → `to: telegram` (보고/제안)
- `from: sentinel` → `to: michael` (트리거)
- `from: michael` → `to: agent:*` (전문가 호출)
- `from: agent:*` → `to: michael` (전문가 보고)
- `from: scheduler` → `to: michael` (루틴 시작 신호)

**원칙**: Gateway는 **우체국**. 편지를 배달할 뿐, 열어보지 않는다.

### Layer 3: 코어 서비스 (Core Services)

Gateway에 직접 연결된 4개의 독립 프로세스.

#### 3a. 마이클 (Michael — 의사결정자)

| 항목 | 내용 |
|------|------|
| **구현** | `src/agent/` (신규: 의사결정 엔진) |
| **역할** | 팀장. 정보를 모으고, 분석시키고, 목표에 맞게 판단 |
| **기동 조건** | 루틴 스케줄 (08/14/21시) 또는 Sentinel 트리거 |

마이클이 기동되면 실행하는 **판단 사이클**:
```
1. 서랍2(state.yaml) 읽기     → "내 자산이 지금 얼마지?"
2. 서랍3(inputs.yaml) 읽기    → "전문가들이 뭘 보고했지?"
3. 서랍1(mandate.yaml) 대조   → "목표에 맞나?"
4. 판단                       → "행동할까, 관망할까?"
5. 서랍4(decisions/) 기록     → "왜 이렇게 결정했는지 남긴다"
6. 사용자에게 보고 (Telegram)  → "브리핑/제안 전송"
```

마이클은 **상주 프로세스가 아니다.** 필요할 때 깨어나서, 판단하고, 다시 잔다.

#### 3b. Sentinel (감시 서비스)

| 항목 | 내용 |
|------|------|
| **구현** | `src/sentinel/` (신규: 경량 감시 데몬) |
| **역할** | 24시간 숫자 감시, 조건 충족 시 트리거 발행 |
| **프로세스** | 항상 상주 (경량) |

```
Sentinel 루프 (영원히):
  1. 외부 API에서 숫자 가져오기 (가격, 잔고, PM 가격)
  2. mandate.yaml의 임계값과 비교
  3. 조건 충족? → Gateway로 트리거 메시지 전송
  4. sleep(interval)
```

**Sentinel은 마이클이 아니다:**
- AI 호출 없음 (가볍다)
- State Store 쓰기 없음 (읽기만)
- 판단 없음 (숫자 비교만)
- 항상 돈다 (마이클이 자도)

#### 3c. Scheduler (스케줄러)

| 항목 | 내용 |
|------|------|
| **구현** | `src/scheduler/cron.ts` (node-cron) |
| **역할** | 정해진 시간에 루틴 시작 신호 발행 |
| **프로세스** | 항상 상주 |

```
스케줄:
  "0 8 * * *"   → { to: "michael", type: "routine", routine: "morning" }
  "0 14 * * *"  → { to: "michael", type: "routine", routine: "midday" }
  "0 21 * * *"  → { to: "michael", type: "routine", routine: "evening" }
  "0 9 * * 1"   → { to: "michael", type: "routine", routine: "weekly" }
  "0 9 1 * *"   → { to: "michael", type: "routine", routine: "monthly" }
```

**Scheduler는 알람 시계다.** 시간 되면 울리고, 그 뒤는 마이클 몫.

#### 3d. Memory (기억)

| 항목 | 내용 |
|------|------|
| **구현** | `src/brain/memory.ts` (better-sqlite3) |
| **역할** | 대화 기록, 사용자 정보, 벡터 검색 |
| **저장소** | `data/memory.db` + `data/memory-index.db` |

Memory는 기존 시스템 그대로 유지. State Store와 **완전 별개**.
- Memory = "지난 대화 기억해?" (과거 지향)
- State Store = "지금 뭘 해야 하지?" (현재 지향)

### Layer 4: State Store (판단 데스크)

| 항목 | 내용 |
|------|------|
| **구현** | `data/state/` (YAML 파일) |
| **역할** | 마이클의 판단에 필요한 모든 것을 담는 4칸 서랍장 |

```
data/state/
├── mandate.yaml      # 서랍1: 목표 (사용자 설정, 거의 불변)
├── state.yaml        # 서랍2: 현재 상태 (포트폴리오 분석가가 갱신)
├── inputs.yaml       # 서랍3: 판단 재료 (각 전문가가 영역별 갱신)
└── decisions/        # 서랍4: 결정 일지 (마이클만 추가)
    ├── 2026-02-15.yaml
    └── ...
```

**접근 권한:**

| 컴포넌트 | mandate | state | inputs | decisions |
|---------|---------|-------|--------|-----------|
| 사용자 | 쓰기 | - | - | - |
| 마이클 | 읽기 | 읽기 | 읽기 | **쓰기** |
| 전문가 에이전트 | - | **쓰기** | **쓰기** (자기 영역) | - |
| Sentinel | 읽기 | 읽기 | - | - |
| Scheduler | - | - | - | - |

### Layer 5: 전문가 에이전트 (Expert Agents)

| 항목 | 내용 |
|------|------|
| **구현** | Python 스크립트 (`.claude/skills/*/scripts/`) |
| **역할** | 각자 전문 영역에서 데이터 수집/분석/실행 |
| **기동 조건** | 마이클이 호출할 때만 실행 |

```
┌─ 정보 수집팀 ─────────────────────────────────────────────┐
│  시장데이터 수집가  │ collect_market.py, collect_binance_api.py │
│  매크로 분석가     │ collect_macro.py                         │
│  뉴스 수집가      │ collect_news.py                          │
│  소셜 감시자      │ Playwright (X)                           │
│  온체인 분석가     │ collect_etf_flows.py, collect_smart_money │
│  PM 스캐너       │ scan_markets.py, monitor_prices.py        │
└───────────────────────────────────────────────────────────┘
┌─ 분석팀 ──────────────────────────────────────────────────┐
│  기술 분석가      │ analyze.py (Claude CLI)                   │
│  리스크 관리자     │ monitor_risk.py (거부권 보유)              │
│  PM 확률 분석가   │ estimate_true_probability.py, kelly        │
│  포트폴리오 분석가 │ sync_balance.py, check_portfolio.py        │
└───────────────────────────────────────────────────────────┘
┌─ 실행팀 ──────────────────────────────────────────────────┐
│  Binance 트레이더 │ execute_order.py, binance_client.py       │
│  PM 트레이더     │ polymarket_client.py, sell_positions.py    │
│  DCA 봇         │ execute_dca.py                            │
│  리밸런서        │ cross_asset_rebalancer.py                  │
└───────────────────────────────────────────────────────────┘
```

**에이전트는 상주하지 않는다.** 마이클이 부르면 실행하고, 결과를 State Store에 쓰고, 종료.


## 프로세스 상주 여부

| 컴포넌트 | 상주 | 이유 |
|---------|------|------|
| Gateway | ✅ 항상 | 메시지 라우터, 모든 통신의 중심 |
| Telegram | ✅ 항상 | 사용자 메시지 수신 대기 |
| Sentinel | ✅ 항상 | 24시간 가격/리스크 감시 |
| Scheduler | ✅ 항상 | cron 루틴 발동 |
| Memory | ✅ 항상 | 동기 SQLite, 요청 시 즉시 응답 |
| **마이클** | ❌ 필요시 | 루틴/트리거 시에만 기동, 판단 후 종료 |
| **전문가** | ❌ 필요시 | 마이클이 호출 시에만 실행, 보고 후 종료 |
